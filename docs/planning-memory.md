## 새 Unity 프로젝트 시작 메모 (2026-10-06)

### 왜 새로 시작하나 (사용자 설명)
- 그래픽·시점을 2D 탑뷰(핫라인 마이애미처럼 그림 회전) + 레이어 분리 도트로 정함. 3D 쿼터뷰(로우폴리 / 도트 렌더링)를 검토했으나, Aseprite 보유·적 다수가 비인간형(3D의 Mixamo 이점 소멸)·레이어 분리로 그림 수가 "쥐는 방식 × 동작"으로 줄어드는 점 때문에 2D로 결정.
- 옛 데모의 문제: (1) UI가 "이게 작동했습니다" 식의 **보여주기**라 별로였다. (2) **재미와 긴장감이 하나도 없었다.** (3) 코드 구조를 사용자가 **이해할 수 없었다**(예: `ExpeditionSession`이 모든 연결을 모으는 중심, HUD가 partial 클래스 여러 개, A/B/C 비교·시험용 씬·빌더·격리 세션이 본 코드에 섞임).

### 새 코드 원칙 (사용자 채택, 추가는 사용자가 나중에)
- 스크립트 하나에 역할 하나.
- 필요해지기 전에는 복잡한 구조(매니저 계층, 추상화)를 만들지 않는다.
- 짠 뒤 무엇을 하는 코드인지 짧게 설명하고, 사용자가 이해한 뒤 다음으로 간다.
- (2026-10-06 추가) 어느 정도 확장성을 챙긴다. 너무 단순하면 "장난으로 게임 만드는 것 같아서" 싫다(사용자). 구조를 넣을 때는 **왜 굳이 이렇게 짰는지** 설명한다. 다만 쓰이지 않을 추상화를 미리 쌓지는 않는다.

### UI 원칙 (사용자 피드백)
- 실제 플레이어에게 내놓는다고 생각하고 만든다. 검증용·보여주기식 안내, 쓸데없는 설명 문구는 화면에 넣지 않는다. 디버그 정보는 콘솔·에디터 쪽에.
- 페이즈 1 화면에 보일 것(AI 제안): 체력, 가방, 탈출 진행 정도.

### 페이즈 기준 (사용자 채택, 2026-10-06)
흐름: **기초공사 → 게임 핵심 확인 → 콘텐츠 확장·심화**. 사용자 설명: 처음부터 긴장감을 확인하기보다 기본 조작감 등 시스템을 확실하게 짜는 기초공사를 착실히 하고, 게임적으로 중요한 부분을 확인해 나간 뒤, 추가 콘텐츠를 만들고 심화할 수 있게 한다.
